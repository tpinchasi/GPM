# Decision Log

> One entry per decision: what was decided, why, and what was rejected. The specification states
> *how things are*; this file records *why*. All entries so far are dated 2026-09-17, the day the
> design was drafted and reviewed. "Owner" is the project owner; "review" is
> [architecture-review.md](architecture-review.md).

| # | Decision | Why | Rejected / not adopted |
|---|---|---|---|
| **D1** | The pool is a separate layer that serves GPU compute; apps only request it. No pool server code in an app, the pool never calls into an app, apps never trigger recovery or spending | Owner requirement: it must be seamless for the app, which should not care where the GPU runs | Infrastructure pushing settings into its consumer; clients shelling out to a provisioner when they notice an outage |
| **D2** | Three host kinds — `local`, `fixed-remote`, `rented-interruptible` — and three transports for remote hosts — `tunnel`, `http`, `https` — as independent properties | Owner requirement | Tunnel-only remote access |
| **D3** | Apps reach the pool through a client SDK whose **default** is to wait and retry when the pool has no capacity. The maximum wait is configurable (per call, per client, by environment) and ships at 30 minutes | Owner requirement. An HTTP transport rather than a wrapper function, so it works under whatever client library an app already uses | Retry as opt-in; a fixed wait |
| **D4** | Strict routing priority: local first (treated as always up), fixed-remote next, rented last | Owner requirement. Side effects are desirable: rented hosts go idle first and carry only overflow | Least-loaded across all hosts; cost- or speed-weighted routing |
| **D5** | Session affinity is off by default | Owner: not required. Kept as an option for later measurement | Soft affinity by default |
| **D6** | Apps request a logical model name; the pool serves the build suited to the host (an Apple-optimised build on Apple silicon, the standard build elsewhere), learning what a host is by cheapest evidence first | Owner requirement | Apps naming platform-specific tags themselves |
| **D7** | Renting, bidding, holding and tear-down are named, configurable strategies; defaults reproduce hard-won existing behaviour (floor plus an absolute premium, ceilings, ingress-aware ranking, re-bid in place before replacing, verified destroy) | Owner requirement; the existing bidding knowledge was paid for in real evictions and download bills | A single hard-coded policy |
| **D8** | An operator console for hosts, bidding, leases and decisions | Owner requirement. Built as one more client of the control API, so nothing is console-only | Config-file-and-logs only; a separate frontend application |
| **D9** | Capacity is **workers per host**, set by hardware capability (illustratively: laptop-class Apple silicon up to 3, an ~80 GB card up to 6), bounded by a memory ceiling for the model set | Owner requirement. Workers are first-class objects so dispatch, resizing and visibility are one mechanism | A single global concurrency number; a bare semaphore per host |
| **D10** | **A lease is the only thing that can spend money**, with mandatory dollar caps and tighten-only overrides | Makes unattended spending safe and reviewable; generalises an existing "nothing spends without an explicit yes" habit | Demand-driven renting without explicit authority |
| **D11** | The framework will be **released publicly**, with its first adopter being the codebase it was designed in | Owner decision. Raises the bar on separation, extension points, safe defaults, robustness, and a contract others can depend on | Internal tooling for one developer |
| **D12** | Scripts that currently use GPUs in the first adopter's repository are **not design inputs** | Owner direction. The framework is specified by what any client, provider and engine need | Arguing design choices from one adopter's timeouts, flags and functions |
| **D13** | Mixed model builds within one multi-call session are **recorded and measured, not prevented**: record (model served, runtime class, host) per call, make it joinable to the adopter's data, compare behaviour per class on the first real run; keep `session_build_consistency` as an off-by-default switch | Owner decision on review F1. A run is cheap to regenerate, and random per-call assignment is itself a sound equivalence test. **Accepted limit:** recording detects mixing but cannot repair a mixed dataset | Making session-level build consistency the default |
| **D14** | Router and supervisor are **two processes** sharing SQLite; the router keeps serving if the supervisor dies. `on_exit: release` is removed: `stop --release` destroys, `restart` keeps and re-adopts, crashes are left to the dead-man timer | Review F2, accepted in full once D11 was stated — isolation has to hold by construction, not by every contributor's discipline. Release-on-exit contradicted adopt-on-restart | One process with slow calls kept off the event loop; implicit release on exit |
| **D15** | A **time budget** in the contract: cancel upstream work on client disconnect; only the client side retries for capacity (router retries once, only for a host that died before first byte); the SDK owns connect / first-byte / between-bytes timeouts; enforced invariant *router queue timeout < SDK time to first byte*; non-SDK clients get an early `503`; optional request deadlines | Review F3. The pool cannot know an arbitrary client's timeout; unrelated waiting layers produce abandoned, billed work | Leaving each layer its own unrelated number |
| **D16** | **The pool is the unit of isolation and has a required API key.** Requests are anonymous; budgets, leases, authority to rent and per-client policy are pool properties; workloads that must be separated use separate pools. Multi-pool management is future work. The **app key** (inference) and **admin key** (control API, console) are separate | Owner decision on review F4 — simpler than per-request identity. The two-key split was a reviewer addition the owner accepted: an app that can request a completion must not be able to spend | Per-request client ids; `interactive` / `batch` request classes; a `gpm run -- <cmd>` lease wrapper (the last is independent and may return) |
| **D17** | **Host trust levels are deferred.** What data may reach which host is recorded as a future requirement | Owner decision on review F5: not a blocker now. The first adopter carries synthetic data | Trust levels per host and a maximum trust level per pool in v1 (the reviewer's recommendation) |
| **D18** | **v1 scope** has a cut line, with three owner musts inside it: all three host kinds, the full console, the dead-man timer | Review F6 plus owner musts. A public v1 has to be dependable; everything deferred is built later from what real use shows to hurt | Shipping the whole design as v1; a read-only console in v1 |
| **D19** | The **dead-man timer** uses the provider's instance-scoped credential; the account credential never goes on a rented machine. Fires on no supervisor heartbeat **and** no inference for 20 minutes; default action destroy | Owner must. The blocking unknown was verified: the first provider injects a per-instance restricted key that can only start, stop or destroy that instance | Stop as the default action (a stopped instance bills storage indefinitely with nobody watching) |
| **D20** | **Build order:** 1 Route (router + SDK over static hosts), 2 Supervise, 3 Console, 4 Release | Review F7. Whether a proxy can carry streaming, tool calls and structured output without changing behaviour is the largest technical unknown and everything depends on it | Relocating existing provisioning code first, which ships nothing usable |
| **D21** | **Prepare a rented host on request**, from the console, API and CLI: rent, load the pool's models, verify, then join / park / destroy. It is its own small lease. Parked hosts are restarted before new offers are bid on; parking is time-limited | Owner requirement. Overflow-driven renting cannot get a host ready ahead of a run or keep one warm between runs | Open-ended parking; borrowing authority from another open lease |
| **D22** | **Catalog-only model resolution** — unlisted names pass through literally, never guessed, never pulled. The contract is stated honestly as the engine's API plus a small versioned pool dialect | Review F9. Guessing a variant name and downloading it is a supply-chain risk, a silent substitution, and an unrequested download. The claim that an app "cannot tell the difference" was untrue once names resolve | A `<name>-<suffix>` convention for unlisted models |
| **D23** | **Every host holds the pool's whole model set, loaded permanently**, in one engine process; a host that cannot hold it does not join; a model outside the set is refused, never loaded on demand. **The queue is first come, first served** — no request classes, no separate lane for short calls | Owner decisions on review F11. The first removes model swapping by construction, which is stronger than the reviewer's proposal to police swaps | Routing on loaded-vs-present with pinned resident sets; an embeddings lane bypassing worker accounting |
| **D24** | **Spend is reconciled against provider-reported charges** every pass; caps enforced on the higher figure less a safety margin. **Providers are driven through their HTTP API, never a CLI** | Review F13, both parts accepted. A hard stop enforced on an estimate drifts; CLI scraping is fragile in an unattended service | Estimate-only accounting; shelling out to a provider CLI |
| **D25** | **Build the router and the supervisor rather than adopt** an existing load balancer or orchestrator | Evaluated Olla, LiteLLM, SkyPilot / SkyServe and dstack against the requirements: some route, some provision, none do both, **none offers programmable bidding**, and none has workers, variant resolution or machine-readable capacity answers. Recorded in [archive/design-2026-09-17-pre-split.md](archive/design-2026-09-17-pre-split.md) §4.4 with sources | Olla with a static endpoint list over stable local ports; LiteLLM (requires apps to switch to another API); SkyPilot (static bid, recovers by relaunching elsewhere and re-downloading) |
| **D26** | Documentation is **split into a generic core and an adopter guide**; **provider, engine and strategy are separate, versioned plug-in interfaces**; variant resolution is keyed by **host capability**, not by one platform; a **threat model** and a **release checklist** exist | Review F14–F18, delegated to the reviewer by the owner. Host kind had been mixing "how a machine is obtained" with "what runs on it", which vary independently | One document doing three jobs; a single host-kind interface; Apple-vs-other as the only resolution axis |
| **D27** | The repository is **GPM** ("GPU Hosts Pool Management"), created private by the owner on 2026-09-17 with no shared history with the first adopter's repository; the docs were moved into it the same day | Owner decision; satisfies the release checklist's "clean repository" item. **Still open:** the identifier set derived from the name — CLI, SDK package, environment-variable and HTTP-header prefixes, configuration directory — which the docs still write as `pool`, `gpm_client`, `GPM_*`, `X-GPM-*`, `gpm` | Splitting the framework out of the adopter's repository history |
| **D28** | **Three dialect items added while building phase 1**, all minor additions under the contract's own versioning rule: `503 no_eligible_host` (hosts are ready but none holds a build that satisfies this request), `504 deadline_exceeded` (the request's `X-GPM-Deadline` passed), and the `X-GPM-Wait-S` response header (time spent queueing) | The contract had no honest answer for two states the router genuinely reaches. Reusing `hosts_unreachable` for "ready but not eligible" would make the machine-readable reason lie, which is the one thing that reason field exists to prevent. A passed deadline needs a code the SDK does **not** retry — the app has already said the answer would be useless — so it is 504, not 503. `X-GPM-Wait-S` is the header behind the `pool_wait_s` fact the SDK was already specified to expose, so queue wait is never mistaken for generation time | Reusing `hosts_unreachable`; answering a passed deadline with `503`, which the SDK's default policy would retry |
| **D29** | **`enforces_schema` is three-valued**: `true` (this build enforces a structured-output schema), `false` (it accepts one and ignores it), and **unstated** (nobody has said). A schema-carrying request never goes to a `false`; an unstated build is usable, but only after every build known to enforce | A boolean defaulting to `false` makes every model with no catalog entry refuse schema-carrying requests — yet an unlisted name is specified to pass through *exactly as requested*, and the pool makes no choice there to protect the app from. The guard exists to stop the pool **choosing** a build that would silently turn guaranteed-valid output into best-effort output; where there is no choice, there is nothing to guard. Defaulting to `true` instead would have the pool assert a guarantee nobody verified | A boolean defaulting to `false` (breaks passthrough for uncatalogued names); a boolean defaulting to `true` (claims an unverified guarantee); refusing schema requests pool-wide until an operator declares a variant |

| **D30** | The **`tunnel` transport drives the `ssh` client** (`ssh -N -L`, supervised as a child process) rather than speaking SSH from Python. Host keys are pinned on first connection (`accept-new`) against a pool-owned known-hosts file; the local port is fixed for a host's lifetime, so a reconnect replaces the process underneath an address the router never has to re-learn | The simpler mechanism, and `ssh` is a standardised, ubiquitous client rather than a churning vendor CLI — `ssh -N -L` produces no output to parse, so the "never a CLI wrapper" rule, which is about providers whose errors arrive as prose, is not in tension. **What it gives up:** structured errors (a failure is a process exit plus a port that stops accepting), and it needs an `ssh` binary present | An SSH library in-process (`asyncssh`): structured errors and programmatic key pinning, at the cost of a large dependency on the server package and a second implementation of the protocol to keep current. Worth revisiting if the coarse failure signal proves insufficient for the supervisor in phase 2 |
| **D31** | **The supervisor runs permanently**, not only while a lease is open. It rents nothing without one, so an idle supervisor cannot spend | Owner decision, answering [roadmap](roadmap.md) §4 Q2. The orphan sweep, parked-host limits and prepare-a-host only mean something *between* runs — an only-while-leased supervisor leaves a stray instance billing until the next lease, which is the exact failure the sweep exists to catch. D21's parking already leaned this way | Starting a supervisor when a lease opens and exiting when the last one closes — simpler, and it cannot leak spending while idle, but nothing then watches what was left behind |
| **D33** | **Offer filters are applied by the pool, not pushed into the provider's query.** The query asks broadly (bounded by a result limit); every hard filter runs locally so each rejected offer keeps the reason it was rejected | Found while building phase 2: pushing the policy into the provider's own query made a filtered market indistinguishable from an empty one, and the operator could never see *which* filter bit. "4 pass, 76 rejected, and here is why" is the whole point of having an offer policy, and the console's market preview is specified to show exactly that | Filtering at the provider for smaller responses — cheaper per call, but it throws away the reasons and makes a misconfigured ceiling look like a dead market |
| **D34** | **A bid the ceilings push below the floor is a refusal, not a bid.** `price_bid` returns no bid, and the offer is rejected with its own `bid:` reason | Seen on the first read-only look at the live market: with the on-demand price mis-mapped, every crossover clamp landed at 0.8 × floor — a number that could never win. Even with the mapping fixed, a ceiling below the floor is the operator saying "not at that price"; placing an unwinnable bid there would only hide that from them | Clamping to the ceiling and bidding anyway (unwinnable, and invisible); raising the bid to the floor (silently overrides the ceiling) |
| **D36** | **The identifier set is `gpm`**: CLI `gpm`, packages `gpm-client` and `gpm-server`, import names `gpm_client` and `gpm_server`, environment prefix `GPM_*`, header prefix `X-GPM-*`, configuration and state under `~/.config/gpm/`, and rented instances labelled `gpm/<pool>/<host>`. The SDK's own class names keep the domain noun (`PoolClient`, `pool_transport`, `PoolUnavailable`) | Owner decision, closing [release-checklist](release-checklist.md) §1.2 and [roadmap](roadmap.md) §4 Q7. `gpm` is short enough to type and matches the project. The label prefix gained `gpm/` because the live run found another tool renting on the same account, and the sweep must be able to tell them apart | CLI `gpmctl` (no collision at all, four more characters every invocation); keeping the working titles `pool` / `gpu_pool_client` / `GPU_POOL_*` / `X-Pool-*`, which the checklist calls too generic for a shared machine and which would break every adopter if changed after publishing |
| **D37** | **Apache-2.0**, with copyright held by **ClearViews**, a `NOTICE` file, and a Developer Certificate of Origin sign-off for contributions rather than a CLA | Owner decision, closing [release-checklist](release-checklist.md) §1.3. A DCO is the low-friction way to record provenance without the paperwork of a CLA. | **D85** | **A price ceiling per accelerator, beside the one per machine.** `offer_policy.max_all_in_per_gpu` divides an offer's hourly price by its card count; both ceilings may be set and an offer must pass each one that is | The owner, looking at a market the pool could not buy from: a machine-level cap refuses every multi-GPU offer on its total price, however good its value. | **D86** | **Every lever that decides a host's fate is editable where hosts are watched, and a lease is changed in one form.** The whole `teardown` block — fifteen fields — reaches the console as sliders and dropdowns; the Leases screen separates open from closed and filters the closed ones; extending a lease is a single form showing what it holds now, not a chain of browser prompts | The owner, after a day of editing the supervisor's own file: every tear-down setting was invisible in the console, so changing how long a stuck host bills meant a text editor and a restart. | **D115** | **A pool holds several workloads, kept apart by construction; the pool as it was is the shared workload.** A workload is a named unit inside the one router and the one supervisor that owns a model profile, a lease (opened by `gpm workload create` from a model, an answer-latency target at p95, a parallelism and a duration, with a dollar cap typed or derived and confirmed), its own rented hosts, its own bearer key (`gpmw_`, stored hashed, valid while the lease is open, shown once, rotated with a grace) and its own sizing: workers per host from the latency target as measured in the request log (unmeasured is said), hosts at the start from the parallelism, scale-up by dynamic allocation inside its lease. **One listener; the key picks the workload**, and a workload key reaches only that workload's hosts — plus, **only while it has no ready host of its own**, a bounded share of the shared workload's ready workers, behind the shared workload's own requests. The machine choice adds one deterministic stage before the advisor, the **rental-kind rule**: on-demand or bid by expected cost over the hours left, eviction rate from the machine history, time to ready and the work a lost host takes with it, returning its reasons; on-demand for the first host and bids for scale-up is what the numbers usually give, not a rule. The pool's caps bound every workload together; a workload whose start would cross one — counting hosts other workloads have reserved and not yet rented — is refused at creation. **Built as one fleet with an explicit unit per demand**, not a fleet per workload: the orphan sweep, adoption, the avoid list and the caps are the pool's, and every decision about one demand is passed its unit. **Any host whose lease is not open is released on the next pass**, drained where it serves, and its spend recorded under its own lease meanwhile — for every lease, shared ones included (D53 held for every way a lease closes, not only its caps and time). **A workload's start is a floor** held for its lease, rented without waiting for load — amending D66's first round of one, for workloads only. **Borrowing's share is pool-wide**, and a borrower yields only to a queued shared request the host could serve. **Room reserved for a starting workload** is not taken by the shared workload, nor by a workload created after it. **A workload's model need not be shared**: a catalog entry marked `workloads_only` sits outside the pool's model set — the shared hosts never fetch it, and an app key is answered as if it did not exist — while a model outside the set and unmarked is still refused, so a mistyped catalog name is still caught (owner, 2026-09-29: "decouple"). **A workload's lease is changed only through its workload** (the generic lease API refuses it), so the router's end time and the workload's state move with it. Creation is serialised, the workload's row written before its lease. Specified in `docs/spec/workloads.md`. **Supersedes the part of D16 that made separate pools the only separation**; the pool stays the unit of spending and of the caps, and D16's key split stands | The owner wants a pool per workload: a model, a latency, a parallelism and a duration in, a secured endpoint out, that an application owner can put in any chat client's network settings; a shared pool that every app may reach with its own key; and a workload that borrows from the shared pool while its own hosts come up. Reviewed against the code before anything was built (STATUS.md, 2026-09-28): the fleet takes the first open lease that allows renting, so leases do not coexist as demands today — the deepest change is a fleet per workload | **A separate GPM per workload** — process isolation, but borrowing across processes needs a proxy in front of both and a second protocol, and the caps would be per process rather than per machine; still available as a deployment for a paying customer. **A key per app inside one workload** (per-client identity) — deferred as before; a workload is the unit. **Time to first token as the target** — buffered delivery already makes it the whole generation. **A workload that may always borrow** — would never need sizing. **Client certificates as the only access** — most chat front-ends cannot carry one; bearer over TLS is what every client supports, mTLS a later option. **Scaling from the latency target** — the owner keeps load-driven scaling; the latency sizes the host, the load adds hosts. **An AI agent choosing machines as the first strategy** — it cannot run in tests without a cloud account and cannot be trusted with a bid unchecked; it is the advisor's place (D69, D70), after the deterministic rule, with the same reasons in hand |
| **D139** | **Keep models between hosts: a checkbox on each provider account, offered only where the provider's storage reaches a data center.** Turned on, each workload renting there gets a *model volume* in its first host's data center, its own and deleted when the workload ends, its storage on the workload's lease; later hosts — scale-up, replacements — copy their models from it. **A host never runs from the volume:** every host keeps its models on its own disk; one host at a time *fills* the volume by copying its verified files up into a fresh directory, renamed into place with a marker naming the hub revision; every other host copies **by the hub's own file list**, never by listing the volume, **checking each file against the hash the hub publishes** (Ollama: each blob against the digest it is named by) and taking anything missing or mismatched from the hub. So the volume is a cache never trusted, and no host can harm another through it. The volume is mounted at paths that are the agent's own constants, given only to hosts the pool creates — **no verb is added (D40, D41)**. The preference for an offer in the volume's data center is capped at the download it saves, priced at the offer's hourly rate (which also bounds D116's warm machine); a data center with nothing in stock is passed over and its hosts fetch from the hub. Both engines. With a volume, hosts at a provider that has one are released, not parked. **Supersedes D116's warm machine as a choice**: a provider whose volumes are bound to one machine (Vast) shows the checkbox greyed, with the reason, and `workloads.keep_models_on_machine` is retired | The owner, 2026-10-07: RunPod sells storage that makes a cold start quicker; per workload first; “this should be a checkbox at provider level — Vast's greyed out, with a tooltip explaining”; both engines; release rather than park. A network volume reads at ~400 MiB/s, slower to load from than a parallel copy to local disk; no provider offers a read-only mount, and RunPod warns that concurrent writers corrupt it. A machine-bound volume helps only when that exact machine is free again — rare on a market — while it bills the whole time. Review found the vLLM launcher keeping its process ids and logs in the models directory, which a reused volume would carry to a new host: they move out of it | **A choice on each workload** — the operator would choose a mechanism the provider decides. **Volumes shared by the pool and outliving workloads** — they would help first hosts too, but need a lease that pays for storage and can never pay for a host, which the lease model cannot express yet; kept for later, decided on the measured times. **The engine loading straight from the volume** — slower, and a host would trust what another wrote. **The filler mounting the volume as its models directory** (D116's way) — the fetch follows links and trusts sizes. **Filling through RunPod's S3 API** — a second account credential. **Vast's machine-bound volume** — kept in the plug-in interface, not offered |

| **D57** | **A model is loaded into memory as soon as its own download finishes, while the rest of the set is still downloading.** Preparation stops being two phases — pull everything, then load everything — and becomes one: each tag is pinned the moment it lands on disk, overlapping the load of one model with the download of the next. The verification that decides readiness is unchanged and still the whole set **together** (§2.2 of the supervisor spec): a host joins when every model is resident at once, never on a partial set, so nothing about what the router may dispatch changes. A load that fails is the same failure it is today, reported against its own tag, and the host is given up rather than joining with a hole in the set | Measured live on 2026-09-20 while a rented host came up: its three downloads ran from 21:03:31 to 21:06:02, and the loading that followed took a further 78 seconds, from 21:06:09 to 21:07:27, before the host reported ready at 21:07:51. That 78 seconds was spent with the GPU idle and the disk already holding two of the three models — dead time on a host that is billing by the hour, on every rental, and it grows with the size of the set | Loading the models as they arrive **and letting the host serve them** before the set is complete — a bigger change than was asked for: it makes readiness per model rather than per host, and the model set exists precisely so that any host the router picks can serve anything in it. Left as an open question for the owner. Pulling the set in parallel as well — the download is the bottleneck and sharing one link between three pulls finishes no sooner, while making the per-model progress the operator watches much harder to read |
| **D56** | **A rented host's worker count can be changed while it runs, as an operator's explicit act.** Lowering takes effect at once and is graceful: the surplus workers drain (§2) and the engine is left alone, so nothing in flight is disturbed. Raising needs the engine to really run the extra slots, so the host drains, its engine is relaunched with the new parallelism, its pinned set is loaded again, and it returns to `ready` — about a minute of that host not serving, reported as a stage like any other preparation. What travels to the host is the same closed set of bounded whole numbers as D41 (`workers`, `models_held`, optional `context`); the relaunch is run by the start-up script the pool installed when it created the host, never by a command sent from the pool. The number is stored with the host, survives adoption, and is still bounded by the memory ceiling (§2.1). **Supersedes D45's "the host keeps it for its life"**: a profile still decides the number before the bid, and still cannot be applied retroactively to a running host — but an operator may now resize one deliberately | The owner, 2026-09-20, measuring a live pool: six rented hosts at six workers each, every host saturated, and latency flat from three to six in flight everywhere — so six was demonstrably not the ceiling on the fast machines, while two contended machines were serving at a quarter of the throughput of an identical hardware label. Tuning either way meant destroying the host and renting another, which re-downloads the model set, so the number that most wants tuning was the one number that could not be tuned | Changing only the router's slots without relaunching the engine — the extra requests would queue inside the engine where the pool cannot see them, and every latency figure the pool reports would be a lie (§2.2). Letting the supervisor resize on its own — a relaunch stops a host serving, and D41 already settled that a restart is an operator's act; evidence-based step-down stays post-v1. Reusing the host agent's restart verb — rented hosts run no agent, and the pool already owns what it created (§1.2) |
| **D55** | **A pool may hold both kinds of rental at once, and an operator may choose the machine.** The market view always lists bid and on-demand offers side by side, each row naming its offer and its kind; **Prepare a host** takes an optional `kind`, or an `offer_id` for one particular row. `rented.mode` becomes what it should have been called: the default for what the pool rents *by itself* (overflow, recovery), not a limit on what an operator rents by hand. A chosen offer is rented **through the same filters, ceilings and caps as any other** — choosing picks among what policy allows, never round it — and if it has gone, lost its bid or no longer passes, **nothing is rented in its place**: the refusal names the offer and says nothing was spent. Each rented host reports whether it can be outbid | The owner: "support mix mode and allow to select the host and type of rent". D52 made the kind a pool-wide switch, so a steady on-demand host beside cheap interruptible ones meant editing configuration between two prepares; and ranking chose the machine, though an operator often knows something ranking does not — a machine that served well yesterday, a location, a card | Substituting the next-best offer when the chosen one is gone: the operator confirmed one machine at one price, and spending on a different one is spending nobody agreed to. Letting a hand-picked offer skip the filters: the list only shows what passes, but it can be minutes old, and a ceiling that bends for a click is not a ceiling. A per-kind host count in configuration ("2 on demand, 3 bid"): the simpler mechanism covers it — prepare what you want steady by hand, let the mode govern the rest — and gives up only the pool *automatically* keeping a fixed mix |
| **D54** | **A rented host is watched while it comes up, and given up when it is plainly not going to.** Three rules, each a number the operator can change: a host whose engine has **never answered** after `max_starting_minutes` (10) is stuck scheduling or starting, and is ended rather than billed for the whole preparing window; a model download **slower than `min_pull_mbps`** (50) sustained for `slow_pull_grace_s` (120) ends the host, with the measured speed beside the speed the offer advertised; and a machine that fails either way — or fails a download for good — is **not bid on again** for `avoid_failed_machine_minutes` (60). The avoided list is applied wherever offers are judged, so the plan, the preview and the real bid agree, and the preview says why a machine is skipped | The owner had been doing this by hand: watching a host sit at "scheduling", or crawl through a download on a machine advertising gigabits, and releasing it. And the pool had no memory — the best-ranked offer *was* the machine that had just failed, so it rented 144381 four times in one evening. The only rule was "not ready after 30 minutes", which has to be long enough for a 30 GB download and so is far too long for a host that never started | Judging speed on the first samples: a download ramps up, and a blip is not a verdict — it is judged over a full window only. Retrying a slow download: the same link on the same machine is just as slow. Persisting the avoided list: a restart forgetting it costs at most one more try |
| **D53** | **A host that is going still finishes what it was given.** When a lease ends, is capped, or a host is otherwise given up while serving, it goes to `draining`: the router stops choosing it — only `ready` hosts are eligible — while the requests already on it keep their workers. It is ended once the router's own busy count reaches zero, or after `teardown.drain_timeout_s`, whichever comes first, and the reason says which. A host with nothing on it is ended at once rather than billed to drain | The owner asked for it, and the state machine had specified `ready → draining` and a `drain_timeout_s` from the start — neither was ever built, so a lease expiring dropped requests mid-flight. The timeout is not a nicety: a host that never finishes is still costing money, so waiting for ever is the wrong failure | Draining every release: an evicted or never-ready host has no work to protect and draining it only bills. Waiting indefinitely for in-flight work: the bill does not wait |
| **D52** | **Non-interruptible (on-demand) rentals are supported**, chosen per pool by `rented.mode` (`interruptible` · `on_demand` · `cheaper`). An on-demand offer carries `interruptible: false`, is created with no price, costs its listed rate, and cannot be outbid; above a ceiling it is **refused rather than clamped**, since a fixed price cannot be bid down; and when one stops, it was not outbid, so the pool releases it instead of re-bidding. Supersedes the v1 deferral in the hosts spec | The owner wanted hosts that cannot vanish mid-run. Everything else already existed — the dead-man timer matters *more* here, because there is no eviction to end a forgotten host — so the work was in telling the two kinds apart everywhere a bid is assumed | A separate host kind: the difference is how it is priced and whether it can be taken away, not how it is reached or prepared. Always preferring one kind: `cheaper` lets the existing score, which already weighs price against the download it would waste, decide |
| **D51** | **The offer search is edited where it is used** — every offer-policy and bidding parameter on the Rented capacity screen, with **Try these** previewing against the live market unsaved, and **Save** writing into `pool.yaml` **in place**: one key changed, comments, ordering and flow style left byte for byte. The file stays the source of truth and the rules stay the file's — validate, plan, retype to loosen. A key the pool cannot place unambiguously (absent, or appearing twice) is refused, never guessed | The owner: "doesn't make sense to go to config and change it each time I want to update my search". Tuning a search is iterative — move a floor, see what passes — and that loop ran through a text editor and a full-file apply | Loading the YAML and dumping it back: it deletes every comment an operator wrote, which is not an acceptable price for changing one number. A regex over the whole file: `workers` appears under hosts *and* rented. Preview-only, leaving saving to the Configuration screen: it is the saving that was tedious |
| **D50** | **"Not ready in time" is measured from when a host entered `preparing`, not from when it was created** — and a host is acted on where it is shown: the lease buttons are one shared control used by both the overview and the Leases screen | A supervisor restart destroyed a healthy rented host eleven seconds after taking it back: adoption marks a host `preparing` so readiness is re-verified, the deadline counted from creation, and the host had existed for 42 minutes. Its twin survived only by being probed first — a race, not a difference. The same flaw hit any long-running host whose engine blinked. The console half is smaller but the same principle: an operator looking at a lease on the overview should be able to act on it there, and two copies of the buttons would drift | Not re-verifying on adoption — assuming a host is still ready across a restart is what adoption exists to avoid. Exempting adopted hosts from the deadline — then a host adopted broken is never given up on |
| **D49** | **A lease can be changed in flight, including raised — extended hours, more dollars, more workers — with the raise confirmed by retyping it.** Tightening stays free. Extending the hours also pushes out the hold on a host prepared under that lease, so the lease cannot outlive the host it was extended for. **Supersedes the tighten-only half of D10**; everything else in D10 stands: a lease is still the only thing that can spend, a lease that may rent still needs a dollar cap, and a lease still cannot loosen a pool-level ceiling | The owner wanted to keep a running host past its hour. Tighten-only did not prevent that spending — the same operator can open a second lease with any cap — it only made them do it in a way that loses the first lease's history and leaves an orphan behind. The real control is the one used everywhere else for loosening: state the worst case, make them type the new value | Allowing a raise silently — loosening is never silent here. A separate "extend" verb — the pool can tell a raise from a tightening by comparing, and one verb keeps the CLI and console honest about which it is |
| **D48** | **One host can be followed while it is prepared**: `GET /pool/hosts/{id}` answers with the host's record, the stage in words, what its engine holds *now*, per-model download progress, and that host's slice of the decision log; the console opens it from any host id and follows it while open. The stage is **derived** from what is known — the provider's own message, whether the engine answers, what is on disk against the model set — never stored, so it cannot drift from the facts it describes. Progress comes from an optional `on_progress` on the engine's `pull`, and an adapter that does not take it still works | The owner, watching a rented host sit at "preparing" for eight minutes with nothing to look at, asked for the detail I had been assembling by hand from three places: the decision log filtered by host, the provider's instance message, and the host's own engine over the pool's tunnel. A host being prepared is exactly when an operator most needs to see inside, and exactly when the console said least | A log file per host — the decision log already holds the events, keyed by host. Storing the stage as a field — it would drift from the facts; deriving it cannot |
| **D47** | **A prepare lease ends with its host.** When a host rented by *prepare* is destroyed or vanishes and no other host holds its lease, the lease is closed, with the host and the reason written on it; nothing is rented in its place — the operator prepares again. **An overflow lease is unchanged:** standing demand, kept open after an eviction so the pool recovers the capacity | Found live: four prepare leases outlived their hosts, one by 18 minutes, each until the owner closed it by hand. It was inconsistent (a prepare that rents nothing already closed its lease) and not harmless: an open lease is spending authority, and its `workers` count as demand, so the pool could rent a replacement nobody asked for — quite possibly on the machine that had just failed to prepare three times | Closing every lease when a host goes — breaks eviction recovery for overflow leases, which is the point of them. Letting a prepare lease rent its own replacement — re-downloads the model set on the operator's money without being asked |
| **D46** | **The spending cap is per host; the overall hourly cap is optional and unset by default.** Every bid is clamped to `bidding.bid_ceiling` and every offer filtered by `max_all_in_hourly`, so the pool's hourly spend is already bounded by `max_rented_hosts × bid_ceiling` — and that worst case is reported wherever limits are shown. `limits.max_hourly_burn` remains for an operator who wants an overall budget below that bound; removing it is loosening and retyped. **Supersedes the $1.00 default of D32**; the rest of D32 stands | The owner raised the host limit to 2 and could not rent a second host: the first sat at $0.777/h under a $0.80 *total*, and the refusal reached him as "no acceptable offer". Two caps expressing one intention — "no host above $0.80" — silently contradicted the host count he had asked for | Keeping a default total: it is the contradiction. Dropping the total entirely: an overall budget is a legitimate thing to want |
| **D45** | **Capacity profiles are built for rented hosts: the worker count comes from the first profile the offer matches, decided before the bid, and the host keeps it for its life.** Matched on the offer's hardware (compared whole), memory and capability. The engine is launched with the same parallelism, so the count is real rather than queue slots. Stored with the host and restored on adoption, because the engine's parallelism does not change when the configuration does. No match → `rented.workers`, shown as a default. A profile carries a `note` for the evidence behind it. Changing a profile needs no retype: more workers on the same host costs nothing more | The owner, after a run: one RTX PRO 6000 Max-Q held 2,765 requests at six in flight with no errors and latency flat from four to six — and asked that the next rental of that hardware start at six. The spec had designed exactly this table (§2.1) and it was never built; the pool used one number for every rented host whatever it was | One `rented.workers` for all hardware — what this replaces. Setting workers when the host becomes ready — too late, the engine is already launched. Recomputing an adopted host from today's profiles — would count workers its engine was never started with. Registering a number above what was observed — six was measured, so six is what is recorded |
| **D44** | **"Could not ask" is never reported as "nothing there", and a provider that says it is being asked too often is asked less often.** A failed offer search is remembered and shown — in the market preview's `problem` field, the console, and the decision log's no-offer reason — instead of rendering as "0 offers seen". On a rate limit the pool backs off (60 s, doubling to 15 min, cleared by the next search that works) rather than asking again next pass | Found live, minutes after D43, in the same shape turned inside out: the provider rate-limited the pool, `_offers()` caught the error and returned `[]`, and the console said the market was empty — which the owner reported as such. An empty market and a pool that cannot see the market are different problems with different fixes, and an operator has no way to tell them apart if they look identical. The throttling itself came from searching every 10 s pass while a lease with unmet demand was open | Raising `probe_interval_s` — treats the symptom and leaves the pool able to hammer a provider under any other setting. Retrying immediately on 429 — that is what earned the 429 |
| **D43** | **A bid is not failed until the pool has proven it left nothing behind — and if that cannot be proven, the pool stops bidding rather than trying the next offer.** The check is made *in the pool*, by label, not left to the plug-in. The Vast client additionally verifies for itself before reporting a lost bid, and its instance listing moved to `/api/v1/instances/` with pagination followed to the end; an unexpected 3xx, and a 410 on anything but an offer, now raise instead of being read as an answer | Found live, and it cost real money: one lease came to be paying for three machines. The provider answered `success: false` to two bids and created the instances anyway, so `create()` raised `BidLost` and the loop moved straight to the next offer, twice. Nothing caught it because `list_instances` had been silently returning an empty list ever since Vast retired the v0 collection endpoint — the bare path 301s, httpx does not follow redirects, and the redirect's body is valid JSON with no `instances` key. That one blind call had disabled the orphan sweep, adoption on restart, **and destroy-verification**, which had been rubber-stamping every destroy as verified for as long as it had been broken. The plug-in contract already said "either an instance or nothing behind"; a contract a plug-in can break silently, on the one path that spends money, has to be enforced by the caller | Fixing only the endpoint — leaves the pool trusting a plug-in's discipline on the spending path, which is the thing that failed. Treating an unverifiable failure as "try the next offer" — that is precisely what stacked the machines up |
| **D42** | **A plan reports every difference between two configurations, by construction**: after the changes it explains in words, anything else that differs is reported generically (`rented.disk_gb changes from 20.0 to 40.0`). And **raising or removing `max_all_in_hourly` or `max_download_per_gb` is loosening**, typed again like the bid ceiling | Found applying a real change: a resized rented block — disk, download estimate, the whole offer policy — moved with the plan listing none of it, because the plan enumerated the settings it knew. An enumeration is wrong the day someone adds a setting; a complement is not. The two price ceilings let the pool pay more, exactly as the bid ceiling does, and had escaped the retype rule only by not being listed | Adding the missing fields to the enumeration — fixes this case and guarantees the next. A test perturbs every setting of a full configuration one at a time and requires a non-empty plan |
| **D41** | **Engine settings reach a delegated host as a closed set of bounded whole numbers** (`workers`, `models_held`, optional `context`), are turned into the engine's own variables by the agent, and are written to a file **whose path the machine's owner set**; the engine is restarted by **the owner's command**; and a restart is **only ever an operator's explicit act**, host id retyped, never the supervisor's pass. The agent reports the settings back as the same numbers | D40 fixed *who* writes the restart command; this fixes *what the pool may say*. If settings travelled as names and values, an admin key could set any variable in the engine's environment — its listen address, a library path — which is code execution by another door. Numbers cannot do that. | **D40** | **An optional host agent, `gpm-agent`, to which an operator delegates a configured host.** It reports facts the engine's API cannot (hardware, memory, disk), from which capabilities are derived; pulls catalogued tags; loads, pins and unloads to make `residency` true; restarts or reconfigures the engine **only through a command the operator wrote into the agent's own configuration**; and deletes a model **only on an explicit console action**, retyped, never for a tag the pool requires there, and never where the machine's owner set `allow_delete: false`. **The pool dials the agent**, over the host's own transport and rules; only the supervisor talks to it; it is never on the request path; its protocol is a closed list of verbs with no "run this". A third key role, never interchangeable with the other two. Level-triggered: the supervisor sends the whole desired state each pass. **Supersedes "the pool never configures someone else's engine" for hosts that run an agent**; without one, nothing changes | The owner, 2026-09-19: adding a host meant pulling models by hand on each machine, typing capabilities nobody checked, and learning from a failed probe that a set did not fit. Those are facts and actions only something on the machine can supply. Pool-dials was chosen because any host whose engine is reachable already has a working path for the agent under rules that already exist, and nothing new listens on the pool | Agentless `managed: true` hosts through the engine API alone — offered first as the simpler mechanism; the owner chose the agent because host-type detection and engine configuration matter, which the engine API cannot give. The agent dialling the pool — needs an off-loopback listener on the supervisor, for hosts that could not serve inference anyway. The agent managing launchd/systemd/Docker itself — elevated rights and much OS-specific code. Never deleting — recommended; the owner chose console deletion, bounded as stated. A general remote-command verb — never |
| **D39** | **A host's residency is a per-host policy: `pinned` (the default) or `on_demand`.** Pinned is D23 unchanged — routable only while the whole set is loaded, and an evicted model takes the host out. On-demand — routable once the whole set is **on disk**; the engine loads a model on first use and may evict it; the request that finds one cold pays the load. **Pulls stay absolute on both**: no request ever downloads, and a tag not on disk keeps the host out until the operator pulls it. Hosts the pool creates are always pinned. Supersedes the "loaded permanently, nothing on demand" half of D23 for hosts that opt in; the rest of D23 stands | D23 was decided for dedicated hosts. On a shared machine — the owner's laptop, also used for other work — it turned the pool off the moment the engine's keep-alive expired, and the only remedy was to pin ~28 GB of models permanently on a 48 GB machine. The principle behind D23 is really two: *never download because a request asked* (supply chain, unrequested multi-gigabyte fetches — a safety property) and *never load because a request asked* (latency, thrash — a trade-off). Only the first is safety; the second belongs to whoever owns the machine's memory | Keeping D23 and telling operators to pin — the quickstart said so; the owner rejected it for the shared-laptop case, rightly. Making on-demand the default — a thirty-second first request is something to opt into, not discover. One pool-wide setting — the laptop and the dedicated box are in the same pool. Letting a request pull on an on-demand host — crosses the safety line for nothing, since the operator lists the tags anyway |
| **D38** | **First-party plug-ins load by entry point** (`gpm.providers`, `gpm.engines`), exactly as a third party's would, rather than from a table inside the framework | The checklist's "no privileged path" only means something if the shipped provider and engine use the mechanism everyone else depends on: a table would let ours keep working while the public path quietly broke. Found still unmet during the phase-4 re-read, after the interfaces themselves were finished | A registry dict with entry points as a fallback — which is the same privileged path with extra steps, and hides a broken entry-point mechanism |
| **D35** | **The configuration file is versioned by the sha256 of its bytes, and a write based on a stale version is refused.** Applied versions are kept beside the file in `<config>.versions/` (last 50) with rollback. The supervisor follows the file by mtime each pass and rebuilds config-derived state in place; a file that does not load leaves the running pool exactly as it was. **The router's listen address and TLS are never changed under a running process** — the plan reports them as needing a restart | The console edits the file *through* the API while an operator may also be editing it by hand, so a lost update has to be impossible: a content hash needs no extra state and detects exactly the case that matters. Keeping versions beside the file rather than in the database means rollback still works when the database is gone, and an operator can read them with `cat`. Reloading in place is what makes "editing the file by hand keeps working" true, and refusing to swap a listening socket underneath live connections is what keeps a configuration change from dropping requests | A monotonic counter in the database (two sources of truth, and useless if the database is lost); no version at all (silent lost updates); restarting both processes on any change (drops in-flight requests and re-downloads nothing but costs the pool its rented hosts' readiness) |
| **D32** | **Shipped defaults are conservative**: `max_spend` has **no default and is mandatory** for a lease that can rent; `max_rented_hosts` 1, `max_hourly_burn` $1.00, `idle_minutes` 10, lease `max-hours` 4, `deadman_minutes` 20, `cap_safety_margin` 10% | Owner decision, answering [roadmap](roadmap.md) §4 Q1. A newcomer's worst case has to be small and obvious on a public framework; the dollar cap stays mandatory because a default dollar figure is exactly the number nobody should inherit silently | No defaults at all — safest, but every invocation becomes a wall of required flags; higher "practical" defaults sized for real work, which enlarge the worst case for someone who leaves a lease open |

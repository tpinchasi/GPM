# Threat Model

> Written against the design, before any code; **re-checked line by line against the
> implementation on 2026-09-19** — §6 maps every threat to the code and the test that provide
> its mitigation. Scope: one pool, one operator or a small team, the supervisor typically on a
> workstation or small server.

## 1. What is worth protecting

| Asset | Why it matters | Where it lives |
|---|---|---|
| **The provider account credential** | It can rent hardware without limit. The most damaging thing to lose | Supervisor's environment, or an owner-only file the supervisor keeps when it was typed into the console (D130). **Never on a rented host, never in pool configuration; it passes through the browser once, as it is typed in, and is never sent back** |
| **Money** | The pool spends unattended | Bounded by leases, caps and the dead-man timer |
| **The admin key** | Opens leases, raises ceilings, releases hosts | Operator's machine; in the console, kept for the tab (`sessionStorage`), or in the browser's profile until Sign out when the operator asks (D137) — the page runs no script but its own |
| **The app key** | Admits a client to the pool's compute | Each app's environment |
| **Prompts and completions** | May be sensitive to an adopter | In transit through the router; in memory on every host that serves them; **never written to the pool's request log** |
| **Availability** | Apps depend on the router | Router process |
| **Integrity of what is served** | An app asked for one model and must not silently get another | Catalog, variant resolution |

## 2. Who might attack, and from where

| Actor | Position |
|---|---|
| A **web page** open in the operator's browser | Can send requests to `127.0.0.1` and to private addresses |
| Another **user or process on the same machine** | Can reach loopback ports, read world-readable files |
| Someone on the **same network** as a non-loopback listener | Can reach the router or control API |
| The **operator of a rented host** | Controls the hardware: can read container memory, disk, environment, and all traffic once it arrives |
| A **compromised or malicious plug-in** | Runs inside the supervisor with its full authority |
| A **malicious model artifact or registry name** | Reaches hosts through a pull |
| A **holder of the app key** | Legitimate client behaving badly, or a leaked key |

## 3. Trust boundaries

```
 browser ──admin key──▶ control API ┐
                                    ├─ supervisor ──account credential──▶ provider API
 app ─────app key────▶ router ──────┘        │
                          │                  └─ SSH / HTTPS ──▶ rented host  ◀── its owner
                          └─ tunnel / http / https ──▶ local and fixed hosts
```

The rented host is **outside** the trust boundary even though the pool created it.

## 4. Threats and what the design does about them

| # | Threat | Mitigation in the design | Residual risk |
|---|---|---|---|
| **T1** | A web page drives the control API on loopback (CSRF, DNS rebinding) and spends money or destroys hosts | Admin key required on **every** control request, as a header, never a cookie; `Host` and `Origin` checked; no ambient authority | A page that can read the key from the console — a browser or extension compromise; and, where the operator ticked *Keep me signed in*, anyone using that browser profile (D137) |
| **T2** | A web page or local process uses the router on loopback for free compute, or to exhaust workers | App key required on every request, loopback included | Anyone who can read the app's environment has the key |
| **T3** | The app key is used to reach the control API | App and admin keys are separate and never interchangeable; the control API refuses the app key | — |
| **T4** | Keys captured on the network | Off loopback, the listener requires TLS; a bearer key over plain HTTP is refused at configuration load | Misconfigured TLS termination in front of the pool |
| **T5** | The account credential is stolen from a rented host | It is **never placed there**. The dead-man timer uses the provider's instance-scoped credential; a provider that has none gets no timer and only short leases. Nothing secret goes in instance-creation environment variables, which the host can read | The instance-scoped credential can stop or destroy that one instance — a nuisance, not a loss |
| **T6** | The pool's own app or admin key is exposed to a rented host | Neither is ever sent to a host; hosts are reached, they do not call back | — |
| **T7** | **The operator of a rented host reads prompts and completions** | **None in v1.** A tunnel or TLS protects the wire, not the machine. Host trust levels are a deferred requirement (D17) | **Accepted and documented:** a pool that includes marketplace hosts must not carry data its owner would not show the host's operator. The provider's "verified" flag raises the bar; it does not make a host trusted. Adopters with sensitive data should run a pool with no rented marketplace hosts until trust levels exist |
| **T8** | A rented host returns tampered output | None beyond corrupt-output detection, which targets faults, not adversaries | Accepted. An adopter needing integrity against a hostile host should not use marketplace hosts |
| **T9** | An app silently gets a different model than it asked for | Catalog-only resolution: only names an operator listed are ever substituted; the model actually served is reported on every response and logged | An operator's own catalog mistake |
| **T10** | A guessed or typo-squatted artifact is pulled onto a host | No pulls by convention or guess; pulls happen only for tags named in configuration, at prepare time, never triggered by a request. On an `on_demand` host a request may cause the engine to *load* a model — a tag already on its disk and named in the catalog — which fetches nothing (D39). Engine images are pinned, never floating tags | A registry serving a different artifact under the same tag — outside the pool's control; pin by digest where the engine supports it |
| **T11** | Runaway spend — a bug, a bad strategy, a market spike | Nothing rents without a lease; leases carry mandatory dollar caps; caps enforced on the higher of estimated and provider-reported spend, less a margin; every bid clamped to two ceilings **after** the strategy returns; rate caps on hosts and hourly burn; one host at a time | Provider-side billing the provider does not report promptly |
| **T12** | The supervisor dies or its machine sleeps while hosts bill | Router keeps serving; dead-man timer on every rented host; lease expiry; orphan sweep at next start; parking is time-limited | A provider without an instance-scoped credential — mitigated by refusing long leases there. **A model volume (D139) has no dead-man timer**: it bills its storage while the supervisor is down, past its lease's end, until the next start's sweep deletes it — cents a day for a model's size, and said here rather than hidden |
| **T13** | Instances nobody knows about keep billing | Provider is the source of truth for existence; label-scoped listing; orphan sweep; every destroy verified by re-listing; **and a failed bid is proven to have left nothing behind before another is placed** (D43). Note what this rests on: all four of those mitigations are the *same* listing call, so a listing that silently returns nothing disables every one of them at once — it now refuses rather than returning a partial or redirected answer | Instances created outside the pool's label — out of scope |
| **T14** | A malicious plug-in exfiltrates the account credential or spends freely | Plug-ins load only if named in configuration. Strategies are pure functions with no I/O, and the supervisor re-checks every cap and ceiling after they return | **A provider or engine plug-in runs with the supervisor's full authority.** Installing one is a trust decision equal to installing the framework. Documented, not mitigated |
| **T15** | A holder of the app key exhausts the pool | Queue timeout, per-request deadlines, cancel on disconnect | No per-client limits inside a pool (deferred). Separate pools are the available control |
| **T16** | Sensitive text leaks through logs or the console | The request log records metadata only — never prompts or completions. Decision events carry numbers and identifiers. Secrets show in the console only as set / missing; a provider credential only as where it comes from and when it was set (D130) | Engine-side logs on hosts are the engine's and the host owner's |
| **T17** | An unauthenticated engine is exposed to the internet | Plain `http` to a public address without auth is refused at configuration load unless explicitly allowed per host; `tunnel` is the default for rented hosts and needs no exposed port | An operator who sets `allow_insecure` |
| **T18** | An SSH man-in-the-middle on first connection to a fresh rented host | Host keys are recorded on first connection and checked after; the address comes from the provider's authenticated API | Trust-on-first-use is weaker than a provider-attested host key, which providers generally do not offer |
| **T20** | A stolen admin key, or a compromised supervisor, drives the agents on every enrolled host | The agent's protocol is a **closed list of verbs with no "run this"**: nothing it accepts is a command, a path or a URL. It starts processes only from literal argument lists in its own source, never through a shell. Restarting the engine runs a command the *machine's owner* wrote on that machine; deletion is refused where the owner set `allow_delete: false` (D40). Tags must be plain model tags — no scheme, path or flag — and pulls stop at a free-disk floor the machine's owner sets. Engine settings cross as bounded whole numbers only, written to a path the owner chose (D41) | Disk filled with catalogued models (bounded by a free-space floor), models deleted that can be pulled again, engine restarts. Never code execution, never traffic |
| **T21** | Someone other than the pool calls an agent | The agent key is required on every call, loopback included; stored hashed, owner-only, compared in constant time; the agent refuses to listen off loopback without TLS unless told to deliberately, and the pool refuses a plain-http agent url off loopback the same way. The three key roles are mutually refused by name: an agent key opens neither the router nor the control API, and neither pool key opens an agent | A stolen agent key exposes one machine's facts, and later its model operations, until rotated (`gpm-agent init --rotate`) |
| **T19** | Another local user reads keys or state | Key files, configuration referencing secrets, typed-in provider credentials and the database are created owner-readable only; the pool refuses to start if they are group- or world-readable | A compromised operator account |
| **T22** | A workload key is used by someone other than its application (D115) | It reaches only its workload's hosts — never the shared pool, another workload, the control API or the directory; it stops at the lease's end even before the supervisor notices; rotation has a grace; where the workload requires one, a client certificate signed by the pool's CA is checked as well | Anyone who can read the app's environment has the key, as with T2 |
| **T23** | A leaked provisioning key spends money (D117) | It is bounded by its grant — workloads at once, dollars per workload, dollars **committed** per rolling day, hours, models, kinds of machine — and by the pool-wide daily cap across every key; a create is idempotent by the workload key's hash, so retries do not multiply spend; unused workloads end by themselves; grants expire and are revoked at once; it can never request a completion or reach the control API | Up to the grant's daily budget, until the key is revoked |
| **T24** | A compromised router spends money through provisioning requests (D117) | The router only records requests. The supervisor treats every row as untrusted input and checks each field again against the named key's grant and the pool-wide daily cap; a key the router did not verify still has to be a key the supervisor issued | Up to the pool-wide daily cap. Before D117 a compromised router had no path to money at all; this is the price of programs provisioning themselves |
| **T25** | A signing request asks for more than a client certificate (D117) | The pool takes only the public key, after checking the request is signed by it; subject, workload, client-authentication usage, not-a-CA and validity are the pool's own; the CA key is read by the supervisor only | — |
| **T26** | A provider credential typed into the console is read back out of the browser or off the wire (D130) | It is sent once, in a request body, only over HTTPS or from the pool's own machine — judged by the connection itself, never by a proxy's headers — and refused otherwise; never in a response, a refusal (validation errors included), an event, a log, the database or the configuration and its versions; every field it was typed into is emptied as its dialog closes | A compromised browser or extension reading the page while it is typed — as T1 |
| **T27** | A settings change redirects a credential to another endpoint, or names another of the supervisor's secrets as one | A typed-in credential is bound to the plug-in's endpoint settings as saved; any change to them deletes it rather than sending it. A credential from the environment goes only to the plug-in's own default endpoint, live or after a restart; one whose settings name an endpoint takes a typed-in credential or none (D134). This also closes a path older than the console: a file edit naming an endpoint and a variable, then a restart. A saved connection is tested only with its own settings | An admin can send a credential they type to an endpoint they name — they hold it already. A `credential_env` may name another variable of the supervisor's, sent to the provider's own endpoint — a third party, not the admin |
| **T28** | A replacement credential, or a changed endpoint, moves a connection to another account, and the hosts on the first are forgotten while they bill (D136) | Refused while the pool holds anything there, unless the new credential sees every instance and volume held — checked under the pass's lock, so no rental slips between; removing a typed-in one, and pointing the connection at another endpoint or credential source — by the plan, a raw save, a rollback or a followed edit — are refused there; a rename drops the old name's plug-in at once, never two on one account | An instance created and never recorded (a crash between the two) is not among what is checked; a file edited while the supervisor is stopped is the operator's, with the shell |
| **T30** | A rented host writes into a model volume other hosts copy from (D139) — to poison what they serve, to make them load or run its bytes, to write outside the volume, or to stall them | No host trusts the volume: a reader copies only the files the hub lists, each checked against the hash the hub publishes (Ollama: the digest a blob is named by), and takes any other from the hub; no link in the volume is followed, and only regular files are opened — a pipe or device is never read; a read that errs or stalls is left to the hub; the engine never runs from the volume. One host fills at a time, writing through a directory it holds open, and renamed into place. What a host's agent says of its volume is bounded input: it can only move the volume between ready, empty and stale, never make, delete or pay for one | A host can waste a volume — fill it with junk, or claim it stale — so later hosts download from the hub as if there were none: slower, never wrong. The volume is a cache whose worst case is its absence |
| **T29** | Test connection is made to fetch what it is told, or to send a secret where it is told | It calls only the plug-in's own operations — the account, one search of a single row, the pool's label. A stored credential is never used with settings sent in the request, and one from the environment only with none: any setting or named variable needs the credential typed in | — |

## 5. Deliberate non-goals

- Confidentiality or integrity against the owner of a host the pool does not control (T7, T8).
- Multi-tenant isolation inside one pool (T15).
- Sandboxing of plug-ins (T14).

Each is stated in user-facing documentation, not only here.

## 7. Reporting

The public repository carries a security policy with a private reporting channel
([release-checklist.md](release-checklist.md)). A finding that lets anyone spend an operator's
money, or obtain the account credential, is treated as critical regardless of how it is reached.
